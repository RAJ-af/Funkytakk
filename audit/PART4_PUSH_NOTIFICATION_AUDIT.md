## Retry

### 1. Retry Mechanism Analysis (`PushNotificationManager.kt:80, 255–350`)
- **Maximum Attempts**: `MAX_RETRY_ATTEMPTS = 3` (`L80`), iterated via `for (attempt in 1..MAX_RETRY_ATTEMPTS)` (`L262`).
- **Backoff Schedule (`L263–267`)**:
  - Attempt 1: Immediate (`0 ms`)
  - Attempt 2: `1500L * (1 shl 0)` = **`1,500 ms` (1.5s)**
  - Attempt 3: `1500L * (1 shl 1)` = **`3,000 ms` (3.0s)**
- **Concurrency Serialization**: Protected by `registrationMutex.withLock` (`L258`).
- **Cancellation Safety**: Catches `CancellationException` (`L335–336`) and rethrows immediately.
- **No Infinite Retry Loops**: Guaranteed termination after at most 3 attempts (`~4.5s` total delay).

### 2. Failure Scenario Evaluation
| Scenario | Behavior in `registerTokenWithRetry` | Assessment |
| :--- | :--- | :--- |
| **Offline (`IOException` / `UnknownHostException`)** | Caught at `L337–345`, logged via `Log.e`, recorded in `debugState.lastError`, retried at 1.5s and 3.0s (max 3 attempts). | **SAFE** (Also re-triggered on foreground resume). |
| **Timeout (`SocketTimeoutException`)** | Caught at `L337–345`, logged via `Log.e`, retried up to 3 attempts with exponential backoff. | **SAFE** |
| **HTTP 401 (`Unauthorized`)** | `ensureActiveSession` (`L290`) does not force-refresh a non-expired or `expiresAtMillis == 0L` cached JWT when the server returns `401`. Attempts 2 and 3 retry with the exact same rejected `authToken`. | **DEFECT** (No forced JWT refresh on `401`). |
| **HTTP 403 (`Forbidden`)** | Logged at `L325–334`. Not treated as a non-retryable permanent error; still executes Attempts 2 and 3 before returning `false`. | **MINOR** (Unnecessary 2 retries on permanent 4xx). |
| **HTTP 429 (`Too Many Requests`)** | Retried up to 3 attempts with 1.5s / 3.0s backoff (`L264, 325–334`). | **SAFE** |
| **HTTP 5xx / Supabase Unavailable** | Logged with HTTP status and error body (`L325–327`), retried up to 3 attempts with 1.5s / 3.0s backoff, then exits cleanly (`L348–349`). | **SAFE** |

## Privacy

1. **Decrypted Plaintext Logged & Displayed in `EncryptedChatRepository` + `SystemNotificationHelper` (`HIGH`)**:
   - When `FunkyFirebaseMessagingService.onMessageReceived` triggers `EncryptedChatRepository.drainPendingDmMessages(applicationContext)` (`FunkyFirebaseMessagingService.kt:51`) while the vault is unlocked in memory, `saveIncomingMessageToLocalDb` (`EncryptedChatRepository.kt:733–744`) passes the decrypted `plaintext` message and `senderTitle` to `SystemNotificationHelper.showSystemNotification`.
   - `SystemNotificationHelper.showSystemNotification` (`SystemNotificationHelper.kt:124`) executes:
     `Log.d(TAG, "System Notification posted successfully: $title - $message")`
     which writes the **sender's name and full decrypted E2EE plaintext message** to Android Logcat in all builds!
2. **Incoming FCM Payload Logged in `FunkyFirebaseMessagingService.onMessageReceived` (`LOW`)**:
   - `FunkyFirebaseMessagingService.kt:33` logs `Log.d(TAG, "onMessageReceived from: ${remoteMessage.from}, data: ${remoteMessage.data}")`, printing the raw FCM `data` map to Logcat.
3. **Lock-Screen Notification Visibility (`MEDIUM`)**:
   - Neither `PushNotificationManager.showPushNotification` (`PushNotificationManager.kt:488–495`) nor `SystemNotificationHelper.showSystemNotification` (`SystemNotificationHelper.kt:110–120`) sets `.setVisibility(NotificationCompat.VISIBILITY_PRIVATE)` (with a redacted `.setPublicVersion(...)`), meaning decrypted DM previews posted when the vault is unlocked in memory are visible on a locked screen unless hidden by OS settings.
4. **Hardcoded Fallback Firebase API Key in Source (`LOW`)**:
   - `GoogleServicesConfig.kt:10` contains `FALLBACK_API_KEY` in source code matching `app/google-services.json`.

## Findings

### [CRITICAL] FINDING 1: Tapping a Decrypted DM Notification Navigates to Non-Existent `"direct_chat"` Route (Blank Screen)
- **Files**: `app/src/main/java/com/example/util/SystemNotificationHelper.kt` (`L95–97`), `app/src/main/java/com/example/MainActivity.kt` (`L38–40, 66–83, 232–448, 489–491`)
- **Problem**: `SystemNotificationHelper.showSystemNotification` sets `putExtra("navigate_to", "direct_chat")` when `partnerUserId` is non-blank (`L97`). When the user taps the notification, `MainActivity` sets `currentScreen = "direct_chat"` (`L80`). However, `"direct_chat"` does not exist in `MainActivity`'s `when (screen)` router (`L232–448`), causing the entire UI to render an empty background `Surface` with no back handler.
- **Additionally**: Notifications created by `PushNotificationManager.showPushNotification` (`L474–478`) attach `data` extras and `"from_push" = true`, which `MainActivity` never reads—so tapping an FCM notification only opens whatever screen was last active instead of opening the conversation.

### [HIGH] FINDING 2: Decrypted E2EE Plaintext Messages Logged to Logcat and Duplicated in System Tray on Push Arrival
- **Files**: `app/src/main/java/com/example/service/FunkyFirebaseMessagingService.kt` (`L41–52`), `app/src/main/java/com/example/repository/EncryptedChatRepository.kt` (`L728–745`), `app/src/main/java/com/example/util/SystemNotificationHelper.kt` (`L82, 124`)
- **Problem**:
  1. `SystemNotificationHelper.kt:124` logs `Log.d(TAG, "System Notification posted successfully: $title - $message")`, exposing decrypted E2EE chat plaintext in system logs.
  2. When an FCM push arrives while the vault is unlocked in memory, `FunkyFirebaseMessagingService.onMessageReceived` first posts a notification via `PushNotificationManager.showPushNotification` (`id = conversation_id.hashCode()`), and then calls `drainPendingDmMessages()`, which posts a **second** notification via `SystemNotificationHelper.showSystemNotification` (`id = (System.currentTimeMillis() % 100000).toInt()`).
  3. Neither notification suppresses display when the user is actively viewing that conversation in the foreground.

### [MEDIUM] FINDING 3: `registerTokenWithRetry` Does Not Force-Refresh Supabase JWT on HTTP 401
- **Files**: `app/src/main/java/com/example/service/PushNotificationManager.kt` (`L290–334`), `app/src/main/java/com/example/SupabaseSessionManager.kt` (`L127–135`)
- **Problem**: If the server returns `HTTP 401 Unauthorized` on Attempt 1 (e.g., JWT with `expiresAtMillis == 0L` or rejected signature), `ensureActiveSession` sees the cached token and returns `true` without refreshing, causing Attempts 2 and 3 to resend the same invalid JWT.

### [LOW] FINDING 4: Duplicate `"messages"` Channel Definitions & Missing Permanent Permission Denial Guidance
- **Files**: `app/src/main/java/com/example/service/PushNotificationManager.kt` (`L71–72, 213–231`), `app/src/main/java/com/example/util/SystemNotificationHelper.kt` (`L19, 36–45`), `app/src/main/java/com/example/MainActivity.kt` (`L44–58`)
- **Problem**: Both `PushNotificationManager` and `SystemNotificationHelper` create channel `"messages"` with slightly different titles (`"Messages & Chats"` vs. `"Messages & Direct Chats"`). In addition, `POST_NOTIFICATIONS` is requested immediately on app launch (before login) with no fallback UI if the user permanently denies the permission.

## Release Blockers

1. **Fix Notification Tap Routing (`MainActivity.kt` & `SystemNotificationHelper.kt` & `PushNotificationManager.kt`)**:
   - Remove or handle `"direct_chat"` in `MainActivity.kt` so tapping a DM notification routes to `"home"` and opens the target `partnerUserId` / `conversation_id` / `group_id` instead of rendering a blank `"direct_chat"` screen.
2. **Remove Plaintext E2EE Logging & Deduplicate Push Notifications (`SystemNotificationHelper.kt:124`, `FunkyFirebaseMessagingService.kt`, `EncryptedChatRepository.kt:738`)**:
   - Never log `$message` plaintext in `SystemNotificationHelper.kt:124`.
   - Avoid posting two separate notifications for the same DM when `onMessageReceived` drains the inbox, and set `NotificationCompat.VISIBILITY_PRIVATE` to protect lock-screen privacy.
